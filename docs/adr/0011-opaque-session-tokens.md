# 0011: Opaque, hashed session tokens in HttpOnly cookies

- Status: Accepted, implemented in Phase 0
- Date: 2026-10-12

## Context
Web sessions need to be secure, revocable, and cheap to check on every request.

## Decision
- Tokens are 256-bit random values, generated by the OS.
- They are sent as an `HttpOnly; SameSite=Strict` cookie (plus `Secure` behind TLS).
- Only `SHA-256(token)` is stored, with a 30-day expiry. Expired sessions are purged
  every 10 minutes.
- Passwords are hashed with Argon2id on the blocking pool, limited to one hash at a
  time per CPU core. Login takes the same time whether or not the username exists.

## Alternatives considered
- **JWT:** no storage lookup is needed, but revocation (logout, compromise) needs a
  denylist anyway, tokens are large, and key rotation adds complexity.
- **Raw tokens in the database** (the prototype): rejected. A database leak would hand
  out live sessions.

## Consequences
- One indexed lookup per authenticated request. At scale, sessions move to Dragonfly,
  with a short in-process cache.
- Mobile and API clients will need short-lived access tokens plus refresh tokens
  (planned).
